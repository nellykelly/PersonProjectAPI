Part I

Foundations

1What the system is

One Flask application serving a personal site plus six self-contained projects. Every project is a blueprint with its own routes, service layer, templates and tests; they share one database, one Redis instance, one worker pool and one deployment.

The important structural idea: routes are thin, services hold the logic, and models hold the state. A route parses the request, calls one service function, and renders. Nothing in app/blueprints/*/routes.py does maths, network I/O, or multi-step orchestration — that all lives in app/services/, which is why the service layer is unit-testable without a Flask request at all.

ProjectRoute prefixWhat it doesCore services
Trading Simulator /projects/trading-simulator Shared public trade book. Open simulated stock/option positions, price them, and run risk (Greeks, scenarios) against a leg, a position, or the whole book. market_data, pricing, instruments, risk_engine, risk_models/, watchlist
QR — Quant Company Scorer /projects/qr-quant-scraper Scores a company 0–100 across four factor categories from SEC filings plus market data, and backtests whether the score predicted forward returns. edgar, quant_score, backtest
Pipeline World /projects/pipeline-world Visitors submit a character; it runs through a real queued 7-stage CI/CD-shaped pipeline, streamed live, and only appears in the world if every stage passes. validators, pipeline, queue, world_cache, analytics

2Runtime topology

Production is a single Hetzner CX22 VPS running five containers from one docker-compose.yml. Only Caddy is reachable from the internet; everything else talks over the internal Docker network and is never exposed publicly.

Constraint worth knowing

Gunicorn runs one process with eight threads, not multiple processes. Flask-SocketIO's threading async mode keeps each client's Engine.IO session in the memory of whichever process created it. With two or more worker processes, consecutive polling requests for the same session get round-robined to a process that has never heard of it and return 400 unknown session, silently breaking Pipeline World's live updates. All concurrency therefore comes from threads, and that eight-slot pool is a real, finite budget — which is why SSE connections are capped (§26) and static files bypass the app entirely (§29).

3Request lifecycle

Every request passes through the same fixed chain of hooks before and after the view function runs. Two of them are registered app-wide in the factory.

  • ensure_session_id — assigns a random UUID4 to session["session_id"] on first visit. This is not authentication. It exists only to scope per-visitor caps (how many positions you may open, rate limits) and to let the browser recognise its own in-flight pipeline submission. Every piece of data on the site is public to everyone.
  • net_monitor hooks — record method, path, Flask endpoint name, status and duration into an in-memory ring buffer. Requests to static and to the analytics endpoint itself are excluded as noise.
  • Flask-Limiter — keyed on remote address, backed by Redis in production so limits hold across restarts.

Outbound calls are logged too, but explicitly at the call site inside market_data.py and edgar.py rather than by a hook, because they are not Flask requests. That is what populates the "outbound" half of the traffic board.

4Application factory

create_app(config_name) is the single construction path, used identically by wsgi.py, worker.py and every test. Order matters here, and the sequence is:

1.  Load config class by name (development / production / testing)
2.  Hard-fail if production is still using the dev SECRET_KEY
3.  Resolve SQLALCHEMY_DATABASE_URI (falls back to instance/site.db)
4.  Init extensions:  db, migrate, limiter, socketio
5.  queue.init_app(app)          -> Redis connection + 2 RQ queues
6.  register_request_hooks(app)  -> net_monitor before/after
7.  register_filters(app)        -> the `money` Jinja filter
8.  Register 10 blueprints with URL prefixes
9.  before_request: ensure_session_id
10. context_processor: site-wide links (GitHub, LinkedIn, resume, email)
11. errorhandler(404)
12. import app.models          (registers mappers)
13. if not production: db.create_all()
Two deliberate asymmetries

Startup fails loudly on a default secret. If config_name == "production" and SECRET_KEY is still dev-insecure-secret-change-me, the factory raises. That value is in the repo's .env.example, so shipping with it would let anyone forge a session cookie. Making it a startup crash means it cannot be forgotten silently.

db.create_all() only runs outside production. create_all adds missing tables but never alters an existing one, so it silently masks schema drift — a column whose type changed in the model looks fine and then fails on write. Production goes through flask db upgrade (Alembic) exclusively; dev and test keep the convenience because a throwaway or in-memory database has no history to preserve.

Why extensions live in their own module

app/extensions.py holds bare, unconfigured instances of SQLAlchemy, Limiter, SocketIO and Migrate. Blueprints and services import db from there rather than from app/__init__.py. Without that split, any module needing db would import the package that imports the blueprints that import that module — a circular import.

Part II

The data model

6Schema overview

Nine tables in three independent clusters. They share a database but no foreign keys cross between clusters — trading, Pipeline World and the game are genuinely separate domains.

The three clusters

  • Trading — Instrument, Strategy, Leg, RiskRequest, RiskResult, plus PriceCache as an unrelated helper table.
  • Pipeline World — Character and PipelineRun.
  • Timed-Squares — TimedSquaresScore alone.
Portability rule

Every column uses a portable type (Integer, String, Float, DateTime, Date, Boolean, JSON), so the whole ORM layer works against SQLite as well as Postgres. Exactly one module breaks that rule on purpose: analytics.py, whose hand-written SQL uses Postgres-only DATE_TRUNC and window-frame syntax (§20).

7Table reference

Instrument — contract reference data

One master row per real-world contract. A hundred visitors trading the same AAPL $230 call expiring the same day all point at a single Instrument, instead of each embedding a private copy of the strike and expiry. Deduped through get_or_create_instrument() on the natural key (underlying_ticker, instrument_type, strike, expiry), which also carries a database-level UniqueConstraint named uq_instrument_identity.

The code column holds the standard OCC option symbol, derived deterministically from the identity fields:

root ticker + YYMMDD expiry + C|P + 8-digit strike (strike x 1000, zero padded)

  AAPL, call, strike 300, expiry 2027-01-15
  -> "AAPL"  +  "270115"  +  "C"  +  "00300000"
  -> AAPL270115C00300000

  stock has no strike or expiry -> code is just "AAPL"

It is stored rather than computed on read so it can be indexed and searched: the instrument catalogue at /instruments is a real lookup by code, not a normalisation detail.

Strategy and Leg — the booking model

A Strategy is a container; a Leg is one booked transaction inside it. Today's UI only ever creates one leg per strategy (named "Single Leg"), but the schema does not assume that — a straddle would be one Strategy with two Legs and needs no structural change.

Leg exposes passthrough properties so routes and templates that used to read a flat position.ticker keep working after the data moved to a separate row:

@property
def ticker(self):     return self.instrument.underlying_ticker
@property
def kind(self):       return self.instrument.instrument_type
@property
def multiplier(self): return self.instrument.contract_multiplier

@property
def signed_quantity(self):
    """Direction applied. Every leg booked today is 'buy',
       so this currently equals quantity."""
    return self.quantity if self.side == "buy" else -self.quantity

side is stored explicitly as 'buy'/'sell' rather than folded into a signed quantity, which is how real booking systems record direction. signed_quantity is the value the pricing maths actually scales by, so a short-selling UI would work without touching pricing.py.

RiskRequest and RiskResult

The central idea of the trading project: risk is not recomputed silently on every page render. A caller submits a request, and that request is a persisted, queryable fact.

ColumnMeaning
scope'leg', 'position' or 'book'. Stored explicitly rather than inferred from which FK is null — a book-level request has both null and would otherwise be indistinguishable from a corrupt row.
scenarioNone for as-of-now, or a shock spec such as {"spot_shock_pct": -10, "vol_shock_pts": 5}. Both in whole percent/points.

JSON null vs SQL NULL

Both JSON columns are declared db.JSON(none_as_null=True). Without that flag SQLAlchemy stores a Python None as the JSON literal 'null', which is not SQL NULL. A query like .filter(RiskRequest.scenario.isnot(None)) would then match every row, making every plain request look like a scenario request.

Character and PipelineRun

Character holds the submission and its current status; PipelineRun is one row per stage attempt, and is the durable evidence the analytics page queries. The name and icebreaker columns are deliberately wider than the validators allow — see §25 for why that headroom is load-bearing.

PIPELINE_STAGES = ("sanitize", "security_scan", "test_uniqueness",
                   "test_profanity", "build", "deploy", "verify")

CHARACTER_STATUSES = ("pending", "sanitizing", "scanning",
                      "testing_uniqueness", "testing_profanity",
                      "building", "deploying", "live", "failed")

There is no "verifying" status. Deploy's own action is writing status="live" — that is what deploying means — and Verify runs afterwards as a read-after-write confirmation without the character passing through another transient state.

Part III

Trading Simulator

8Booking model

A shared, anonymous, public trade book. Anyone can open a simulated position; everyone sees every position. No accounts, no real money, prices roughly 15 minutes delayed.

Opening a position

POST /open is the only write path into the book. Its sequence:

1. Validate ticker against TICKER_WHITELIST      -> 400 if unknown
2. Enforce per-session open-strategy cap (10)
3. Fetch the current underlying price            (market_data)
4. For options: fetch the chain, find the strike, read its implied vol
5. get_or_create_instrument(...)                 -> dedup on identity
6. Create Strategy("Single Leg")
7. Create Leg(side="buy", quantity, entry_price, entry_iv, ...)
8. Commit

Entry price for stock is the underlying price. For an option it is the contract's own last traded price, and the contract's implied volatility is captured into entry_iv at that moment. That captured IV is what every later reprice uses.

Why entry IV is held constant

yfinance exposes an option chain — strikes, bid, ask, open interest, implied volatility — but no Greeks. There is also no live volatility surface available. So positions are repriced with a local Black-Scholes calculation fed by the IV captured at entry and the current underlying price. A real desk reprices off a fresh surface; this is a documented simplification, and it is the honest answer to "where do your Greeks come from".

Rate limiting on this endpoint

Two independent controls, because they stop different things. Flask-Limiter caps POST /open at 10/hour per IP, which bounds automated abuse. The per-session cap of 10 open strategies bounds how much one visitor can clutter a shared public book, which an IP limit alone would not (the cap persists; the rate limit window rolls).

9Pricing and Greeks

app/services/pricing.py is pure maths — no Flask, no I/O, no database — which makes it directly unit-testable. It is the module most worth being able to talk through line by line.

Black-Scholes price

d1 = [ ln(S/K) + (r + sigma^2/2) * T ] / (sigma * sqrt(T))
d2 = d1 - sigma * sqrt(T)

call = S * N(d1) - K * e^(-rT) * N(d2)
put  = K * e^(-rT) * N(-d2) - S * N(-d1)

N() is the standard normal CDF, implemented as 0.5 * (1 + erf(x / sqrt(2))) using math.erf — no SciPy dependency for one function. The rate is a flat RISK_FREE_RATE = 0.045, an assumed constant rather than a live curve.

Boundary case: when T <= 0 or sigma <= 0, d1 and d2 are undefined (division by zero), so the function returns intrinsic value: max(S-K, 0) for a call, max(K-S, 0) for a put. An expired option is worth exactly its payoff.

Greeks, and the quoting conventions

This is where the code makes a deliberate choice that is worth explaining: the raw calculus units are converted to the units traders actually read.

GreekMeaningConversion applied
DeltaChange in value per $1 move in the underlyingNone — already in [-1, 1] per share
GammaRate of change of delta per $1 moveNone
ThetaValue lost to time decay/ 365 → per calendar day, not per year
VegaValue gained per unit of implied vol/ 100 → per 1 vol point (20%→21%), not per 100%
RhoValue gained per unit of interest rate/ 100 → per 1 percentage point

Gamma and vega have identical formulas for calls and puts; only delta, theta and rho carry a term or sign that flips with option kind:

gamma = pdf(d1) / (S * sigma * sqrt(T))
vega  = S * pdf(d1) * sqrt(T) / 100

call:  delta = N(d1)
put:   delta = N(d1) - 1

At the boundary (expired or zero vol) delta collapses to 0 or 1 for a call, 0 or -1 for a put, and every second-order Greek is 0 — there is no optionality left to be sensitive to anything.

From per-share to position level

position_greeks() scales the per-share figures by signed_quantity × multiplier (100 for options, 1 for stock). Stock is special-cased entirely: delta 1.0, every other Greek 0 — holding shares has nothing convex, time-decaying or vol-sensitive about it.

Worked example
Position: 2 AAPL 230 calls, expiring in 30 days, entry IV 25%
Underlying now: $235

T          = 30 / 365            = 0.0822
per-share  delta ~ 0.62,  gamma ~ 0.031,  theta ~ -0.09,  vega ~ 0.11
multiplier = 100,  quantity = 2  -> scale = 200

position delta = 0.62  * 200 =  124     ($ per $1 AAPL move)
position gamma = 0.031 * 200 =    6.2
position theta = -0.09 * 200 =  -18     ($ lost per calendar day)
position vega  = 0.11  * 200 =   22     ($ per 1 vol point)

PnL

cost_basis   = entry_price   * signed_quantity * multiplier
market_value = current_value * signed_quantity * multiplier
pnl          = market_value - cost_basis
pnl_pct      = pnl / abs(cost_basis) * 100

abs() on the denominator matters: a short position has a negative cost basis, and without it the sign of the percentage would invert.

The Hull-White extension — IR Vega

IR Vega is sensitivity to interest-rate volatility. Under a flat constant rate that is structurally impossible: a constant has no volatility to be sensitive to. Rather than fabricate the number or omit it, the module adds a clearly separated one-factor Hull-White short-rate model, used only for this measure.

dr(t) = (theta(t) - a*r) dt + sigma_r dW(t)

Assuming zero correlation between the rate and equity Brownian motions,
the standard result is: price with ordinary Black-Scholes but replace the
equity variance with an adjusted total variance --

  adjusted_variance = sigma^2 * T  +  sigma_r^2 * integral[0,T] B(u,T)^2 du
  B(u,T)            = (1 - e^(-a(T-u))) / a

That integral has a closed form:
  (1/a^2) * [ T - (2/a)(1 - e^(-aT)) + (1/2a)(1 - e^(-2aT)) ]

ir_vega is then a central finite difference: bump sigma_r up and down,
reprice both, divide by 2*bump.

Both parameters (a = 0.03 mean reversion, sigma_r = 0.01 rate vol) are assumed illustrative constants, not calibrated — yfinance has no cap or swaption vol surface to calibrate against. Everything else on the same row still comes from the ordinary flat-rate maths.

10Risk request flow

The chain is position → risk request → report. A caller submits a request against one of three scopes; the pricing happens on the worker container; the result is persisted and rendered.

The single market snapshot

This is the reason position-level pricing exists at all:

def take_market_snapshot(legs) -> dict:
    snapshot = {}
    for leg in legs:
        if leg.ticker not in snapshot:
            snapshot[leg.ticker] = market_data.get_last_price(leg.ticker)
    return snapshot

One price per distinct ticker, fetched once, before any leg is priced. Pricing legs one at a time as they are reached would mark a two-legged spread against two different instants, and the net Greeks would then describe a position that never existed at any single moment. The snapshot is stored in totals so the report can prove what it was marked against.

Crossing the process boundary

Exceptions do not cross processes — the row does

Once pricing moved to the worker, submit_risk_request could no longer wrap the pricing call in try/except: the code that might raise MarketDataError now runs somewhere else with its own database session and its own stack.

The protocol instead is: the worker catches its own exceptions and writes a plain-text reason onto the row (error = "market_data: ..."). The waiting web process re-derives the same exception type from that string once the row stops reading pending, so every existing route's except MarketDataError handler keeps working without knowing pricing moved. The shared database row carries both the result and the failure, because there is no shared call stack to unwind.

The wait itself uses a plain column query, not session.get():

status = db.session.query(RiskRequest.status).filter_by(id=rid).scalar()

session.get() can be served out of this session's identity map without touching the database at all, so it would keep re-reading the stale 'pending' this process already cached and the loop would never terminate. Timeout is 20 s, a ceiling for a dead worker rather than a tuned latency.

Keyword-only arguments

submit_risk_request takes only keyword arguments. It previously took a leg id positionally; adding strategy_id meant a stale submit_risk_request(42) would silently be reinterpreted as "price position 42" — a wrong answer with no error. Keyword-only turns exactly that mistake into an immediate TypeError. When the change landed, 11 old call sites in the test suite failed loudly instead of quietly pricing the wrong thing.

11Model registry

A textbook Strategy pattern. A request names which model runs; the report records which one answered. Adding a model means writing a class and registering it — nothing in the engine, routes or templates hardcodes a model's identity.

MethodReads Greeks straight out of the closed-form Black-Scholes partial derivativesReprices the position at each rung of a spot ladder (−20% to +20%) and reports observed P&L
CostNo repricing loop — a whole book revalues in millisecondsOne pricing call per rung

The separation that makes this work

The engine owns everything with a side effect — the market fetch, the scenario shock, the database writes. The model owns only the maths and receives a frozen PricingContext. Two consequences:

  • Two models answering the same request see byte-identical inputs, so a disagreement between them is a real signal about the models, not about the data.
  • A model can be tested with no network and no database — construct a context, call run, assert on the output.

Canonical vs. measures

ModelRun.canonical fills the fixed RiskResult columns that the dashboard and live feed already read. measures is the model's own ordered, self-describing output for the report page, and extras is free-form JSON for structural output such as the revaluation ladder. That split is what lets a new model report something the schema was never designed to hold without a migration.

Analytic vs. scenario gamma

Both appear on a report and they are genuinely different computations:

  • gamma — the closed-form second derivative. The formula's curvature at a point.
  • scenario_gamma — empirical bump-and-revalue: reprice at spot ±1% around the run's own base and measure how much the P&L itself curves. This is what "scenario gamma" means on a risk desk.

For vanilla Black-Scholes with no exotic kinks the two should agree closely, which makes the comparison a useful self-check. ir_delta is simply rho relabelled the way a risk book would name it: sensitivity to the discount rate.

12Market data

Every yfinance call in the app goes through market_data.py, which layers four things around the raw call.

  1. Whitelist first. No user-supplied ticker ever reaches yfinance unvalidated.
  2. Short-TTL cache. PriceCache is a real table keyed by ticker, 60 s TTL. With a shared public book, many visitors view the same tickers simultaneously.
  3. Retry with linear backoff. Three attempts, 1.5 s and 3.0 s pauses. yfinance's free tier does return 429s.
  4. Clean failure. Everything becomes MarketDataError, and routes render "market data temporarily unavailable" rather than a 500.
NaN is not valid JSON

Illiquid option contracts routinely have no bid, and pandas represents that as NaN. Python's own json module accepts a bare NaN token as a non-standard extension — so testing the endpoint with curl | python -m json.tool looked completely fine. A browser's JSON.parse follows the actual spec, where NaN is a syntax error, and rejected the entire response; one missing bid took out the whole option chain in the UI.

The fix converts every NaN to None before serialising:

df[cols].astype(object).where(df[cols].notna(), None).to_dict("records")

The regression test uses a strict JSON parser (parse_constant raising on NaN/Infinity), plus a second test proving that strict parser would itself reject NaN — otherwise the guard could quietly stop testing anything.

13Watchlist and SSE

There is no free real-time market stream: yfinance is a pull-only wrapper over a REST endpoint, and genuine exchange streaming is a paid integration. The watchlist builds the live feel from polling plus push.

Two guards keep this from burning rate-limit budget for nobody:

  • Lazy start/stop. The poller thread only exists while at least one tab is subscribed, and checks mid-sweep so it stops early if the last viewer leaves halfway through the ticker list.
  • Market hours only. A plain Mon–Fri 09:30–16:00 America/New_York check. It deliberately does not know about market holidays — a documented simplification, not a real trading calendar.

Broadcast uses put_nowait into each subscriber's bounded queue and swallows queue.Full: a stalled viewer must not block updates for everyone else.

The current_app trap in a generator

Flask pops the request context as soon as a view function returns. An SSE view returns Response(generator(), ...) immediately, and the generator body only executes later when the WSGI server iterates it — by which point the context is gone, and any current_app access inside raises RuntimeError: Working outside of application context.

The fix is always the same: capture the real object with current_app._get_current_object() before defining the generator, and pass it in. The background poller thread needs the same treatment, since it has no request context of its own to resolve the proxy through.

Part IV

QR — Quant Company Scorer

14EDGAR and XBRL

Scores a company 0–100 across four factor categories, combining SEC filing fundamentals with market data, then validates the score against realised forward returns.

Data sources

  • SEC EDGAR — data.sec.gov's official public XBRL "company facts" API plus the published ticker→CIK mapping. This is SEC's own programmatic API, not HTML scraping, and requires only an identifying User-Agent per their fair-access policy. Revenue, net income, assets, liabilities, equity, current assets/liabilities, operating income, interest expense, D&A, cost of revenue.
  • yfinance — price, market cap, trailing P/E, price-to-book, and historical prices for the backtest.

Concept aliasing

XBRL tag names vary by filer. One company reports Revenues; another reports RevenueFromContractWithCustomerExcludingAssessedTax; a third uses SalesRevenueNet. Each logical concept is therefore resolved through an ordered alias list, first tag that has data wins:

CONCEPT_ALIASES = {
    "Revenues": ["Revenues",
                 "RevenueFromContractWithCustomerExcludingAssessedTax",
                 "SalesRevenueNet"],
    "NetIncomeLoss": ["NetIncomeLoss", "ProfitLoss"],
    "InterestExpense": ["InterestExpense", "InterestExpenseDebt",
                        "InterestAndDebtExpense"],
    ...
}

Facts are then filtered to annual 10-K filings in USD, deduplicated by fiscal year keeping the latest-filed version (so a restatement supersedes the original), and sorted oldest to newest.

Point-in-time correctness

Avoiding look-ahead bias

get_fundamentals(ticker, as_of_date) filters by filing date, not period-end date:

annual = [f for f in _annual_facts(facts, key)
          if datetime.strptime(f["filed"], "%Y-%m-%d").date() <= as_of_date]

Scoring a company "as of one year ago" needs the fundamentals that were actually public then. A fiscal year ending in December is not filed until the following February or March; using period-end would hand the backtest information nobody had at the time, and any correlation it found would be an artefact. This one filter is what makes the backtest honest.

    frac = 1 - frac
score = round(frac * 100, 1)

Bounds are deliberately broad heuristics, not sector-tuned — a documented v1 choice. Example: P/E has lo=5, hi=40 and is lower_better, so a P/E of 12 gives frac = (12-5)/35 = 0.2, inverted to 0.8, scoring 80.

Renormalising weights — the part worth explaining

Missing XBRL tags are common in practice. Three possible responses, only one of which is defensible:

  • Error out — makes the tool useless for real companies.
  • Treat missing as zero — actively wrong; it scores the company as terrible at something unmeasured.
  • Drop the metric and renormalise over what remains — what the code does.
def compute_overall(category_scores, weights):
    available   = {c: w for c, w in weights.items()
                   if category_scores.get(c) is not None}
    total       = sum(available.values())
    if total == 0:
        return None, {}
    normalized  = {c: w / total for c, w in available.items()}
    overall     = sum(category_scores[c] * normalized[c] for c in available)
    return round(overall, 1), normalized

With equal 0.25 weights and growth unavailable, the remaining three each become 0.333. The response returns both weights_configured and weights_used, so the page can show that the composite was computed over three categories rather than four.

Weights themselves come from app.config["QR_WEIGHTS"], overridable per-category by environment variable — configuration, not hardcoded logic.

16Backtest

For each ticker in a small basket: score it using only fundamentals filed on or before ~1 year ago, take the actual price then and now, and compare the historical score to the realised forward return. Reports a per-ticker table plus a Pearson correlation across the basket.

r = sum((x - mean_x)(y - mean_y)) / sqrt( sum((x - mean_x)^2) * sum((y - mean_y)^2) )

Hand-rolled rather than importing numpy for one function — the same call made for the traffic board's percentile function. Returns None for fewer than two points or zero variance, rather than dividing by zero.

The basket is deliberately smaller than the full trading whitelist (12 tickers) because each one costs two EDGAR calls plus two yfinance calls, and both are rate-limited on unauthenticated use. The endpoint is capped at 5 requests/hour and results are cached for an hour.

This is presented as demo-scale validation — a handful of tickers, one lookback window — not a rigorous research backtest.

17The seven stages

A visitor submits a character — a name, a pick from fixed appearance lists, and answers to four fixed icebreaker questions. No code is ever submitted or executed. That submission runs through a real queued seven-stage pipeline, streamed live to every connected viewer, and only reaches the world if every stage passes.

What makes each stage real

Every stage does four things, in order: emit a start event carrying the actual pseudo-commands it is about to run (this is what fills the live build log), sleep its delay, run its check function, and emit pass or fail while writing a PipelineRun row.

STAGE_COMMANDS["test_uniqueness"] = [
  "SELECT id FROM characters WHERE lower(full_name) = lower(:name) AND status != 'failed'"

]

The check functions are the same functions covered by tests/test_validators.py — not a parallel "pretend" implementation. The spec asked the test stage to run "an actual small test suite"; invoking pytest.main() per character inside a worker loop is slow, fragile, and awkward to feed data into, so the choice made instead was to reuse genuinely tested code. That is a documented trade-off, not a free lunch.

Failure stops the run

if not _run_stage(character, "sanitize", "scanning", _sanitize, "...", fast_mode):
    return                      # <- no later stage executes
if not _run_stage(character, "security_scan", ...):
    return
...

Because a failed stage returns early, no later PipelineRun row is ever written. The tracker table renders those cells as "not reached" — a PASS can never appear to the right of a FAIL. _fail() sets status='failed', records the reason, invalidates the world cache (defensively, in case Deploy had already gone live) and emits the fail event.

Why the catch-all except exists

_run_stage originally caught only ValidationError, on the assumption that was the only way a check could fail. In production a stage crashed for an unrelated reason — most likely the worker container being killed mid-job by a redeploy. That bypassed the handler entirely: no PipelineRun row, no fail event, and because Verify runs after Deploy already committed status='live', a character was left stranded live with a blank gap in its own history. Not failed, not passed — missing, which the UI had no way to render as an error because nothing had raised one it was watching for.

Now any exception ends the stage the same way, with a generic visitor-facing message and the real traceback sent to the app logger. The lesson: a try/except scoped to the errors you expect is a statement about the happy path, not a safety net.

Fast mode

Normally each stage sleeps a fresh random 1–10 s so the run is watchable. A Redis-backed flag toggles that off at runtime, and the page shows real per-stage benchmarks computed only from fast_mode=True runs — slow-mode durations include the artificial sleep and would make the numbers meaningless.

18Join to live

Nothing is validated before enqueueing

A deliberate design correction

The first version validated at the route: charset, injection and profanity checks ran upfront so an obviously-bad submission never became a job. It looked sensible and it broke the product. A visitor who typed a blocked word got a red message under the form and no pipeline run at all — so the single most interesting thing the project does was the one thing nobody could ever watch happen.

Now prepare_join_submission() only strips whitespace and truncates each field to its column width. Every rule lives in exactly one place: the stage that owns it. The form carries no required attributes and no client-side checks for the same reason.

The generalisable point: "fail fast" and "fail visibly" are different goals, and validating early can delete the observability that was the point of building the thing.

The one exception: last-name collision

Still resolved at the route, because it is not a rejection. It is a warn-and-continue prompt ("A Koskela already exists — continue anyway?") that needs a human yes/no before there is anything to enqueue. Answering yes proceeds normally. It has no pass/fail stage precisely because it is not a pass/fail question.

Uniqueness is checked only in its stage

Two visitors submitting the same name back-to-back are both accepted and genuinely race through the pipeline; whichever loses fails visibly at Test: Uniqueness. Checking upfront would have turned that race into a silent rejection at the form.

Self-collision

check_full_name_collision takes an exclude_character_id parameter. By the time the pipeline's own stage runs, the character is already the row in the database being checked against — without the exclusion every single run failed at that stage, 100% of the time. The same function is called from two places with different correctness requirements: pre-insert at the form, post-insert inside the pipeline.

19Cache-aside

The live world state — which characters exist and where — is cached in Redis using the cache-aside pattern with both a TTL and explicit invalidation.

TTL alone would mean a newly-deployed character might not appear for up to 30 seconds. That is fine for many caches and wrong here, where "does this feel live" is the actual product requirement. Explicit invalidation handles the common case; the TTL is the safety net if an invalidation is ever missed. Both mechanisms together are the pattern — either alone is a weaker version of it.

Hit and miss counters are plain Redis INCRs, surfaced on the SRE Infra dashboard as a live hit-rate.

20Analytics SQL

Five hand-written queries over pipeline_runs, each rendered on the page alongside its own SQL in a <details> block so a reader can check the claim. This is the one Postgres-only part of the app.

Mean time between failures — window function
WITH failures AS (
    SELECT started_at,
           started_at - LAG(started_at) OVER (ORDER BY started_at) AS gap
    FROM pipeline_runs
    WHERE status = 'fail'
)
SELECT AVG(EXTRACT(EPOCH FROM gap)) AS mean_seconds_between_failures,
       COUNT(*) AS failure_count
FROM failures
WHERE gap IS NOT NULL

LAG pairs each failure with the previous one; the first row has a null gap and is excluded from the average.

Rolling 7-day pass rate — window frame
WITH daily AS (
    SELECT DATE_TRUNC('day', started_at)::date AS day,
           COUNT(*) FILTER (WHERE status = 'pass')::float / COUNT(*) AS pass_rate
    FROM pipeline_runs
    GROUP BY 1
)
SELECT day, pass_rate,
       AVG(pass_rate) OVER (
           ORDER BY day
           ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
       ) AS rolling_7day_pass_rate
FROM daily
ORDER BY day

COUNT(*) FILTER (WHERE ...) is the SQL-standard conditional aggregate; the ::float cast avoids integer division. The explicit ROWS BETWEEN 6 PRECEDING AND CURRENT ROW frame is what makes it a true trailing seven-row window rather than a running average.

The other three: success rate over time (DATE_TRUNC + GROUP BY), slowest stage (AVG(EXTRACT(EPOCH FROM ended_at - started_at)) grouped by stage), and appearance duplication counts.

Why Postgres specifically

DATE_TRUNC, FILTER and the window-frame syntax are Postgres dialect. Rewriting them in a database-agnostic subset would mean either dropping the window functions or faking them with Python loops — which would undercut the exact thing the page exists to demonstrate. run_metric() checks db.engine.dialect.name and raises a clear AnalyticsUnavailable explaining how to point DATABASE_URL at Postgres, rather than failing obscurely on SQLite. run_all_metrics() isolates each query so one failure does not take down the others.

21Production Town

A canvas viewer on its own page, drawing only characters that cleared Deploy. Split from the tracker page because cramming pipeline mechanics and the world into one small canvas made neither read clearly.

Movement

Two different movement systems, chosen by cost:

  • Grid BFS pathfinding (findGridPath) — used once per spawn, for the long walk from the spawn point to the park. Straight-line steering genuinely gets stuck oscillating against a wall over a walk that long; a coarse BFS on a 6 px grid guarantees arrival.
  • Direct steering with wall-bounce (steerToward + applyMovement) — used for ordinary wandering and for seeking a nearby character. Cheap, runs every frame, no pathfinding.

applyMovement is axis-separated collision: it tests each axis independently so a character sliding along a boundary keeps moving on the other axis instead of stopping dead — standard 2D tile collision.

Conversations

Because every visitor answers the same four fixed questions, two characters who wander close enough can match on a topic and hold a scripted back-and-forth built from both of their answers. That only works because the question set is fixed and shared rather than picked per visitor — there would be nothing to match on otherwise. Cooldowns and a busy-set prevent a character being in two conversations at once.

An environment bug that looked like an AI bug

The reported symptom was "none of the characters are ever talking". The seek logic, notice radius and conversation trigger distance were all correct. The cause was the map: it was a 4×3 grid of city blocks with buildings, and direct steering with wall-bounce has no way to route around an obstacle — two characters who had genuinely noticed each other would bounce against the wall between them indefinitely.

The fix was not a smarter algorithm. It was replacing the block grid with one large open field, keeping a thin row of landmark buildings along one edge as backdrop. A "two agents cannot find each other" bug can look like a search problem when it is an environment-design problem.

The point of the middle row

Two Windows-specific findings

  • RQ's default Worker forks. It calls os.fork() per job, which does not exist on Windows. Naively "just run an RQ worker" would have worked only in Docker and never on the dev machine. 23Site Traffic Analytics

An aggregate board over the application's own traffic. The scoping is the point of the project.

Legal scoping, decided first

Capturing arbitrary visitors' browsing traffic is treated as wiretapping in most jurisdictions regardless of intent, and would violate essentially any host's terms of service. So this captures exactly two things: inbound requests the app receives on its own routes (via app-wide hooks) and outbound calls the app itself makes (logged at the call site in market_data.py and edgar.py). It never touches a visitor's browsing.

Implementation

  • Bounded ring buffer — a thread-safe collections.deque(maxlen=500) behind a lock. Not persisted: this is a rollup over recent traffic, not an audit trail, and resetting on restart is an acceptable simplification.
  • Percentiles hand-rolled — linear interpolation matching numpy's default convention, ~12 lines rather than a dependency. p50 alone hides the slow tail that actually matters; p99 surfaces it.
  • Grouped by Flask endpoint name, not raw path. Grouping by path would fragment every dynamic route (/positions/7, /positions/8, ...) into its own row instead of one meaningful trading.position_detail row.
  • 4xx and 5xx counted separately — a wave of not-founds and a wave of server errors mean very different things.
  • Adaptive volume buckets — a fixed number of equal-width buckets spanning the buffer's own oldest-to-newest timestamps, so a quiet site and a busy one both render sensibly instead of mostly-empty buckets.
The pseudo-URL host-grouping bug

yfinance manages its own HTTP client, so there is no real URL to log — calls are recorded as yfinance://AAPL/info. The "group outbound calls by host" logic did a naive target.split("/")[2], correct for https://host/path but reading the ticker as the host for the synthetic scheme. The dashboard grouped by ticker symbol instead of by service. Fixed by branching on whether the target is a real http(s):// URL (extract hostname) or anything else (use the scheme name).

The page polls /api/analytics every 5 s rather than holding an SSE connection — an aggregate rollup does not need a push per entry, and 5 s staleness is unnoticeable for a board of averages. That removed a whole SSE category and its concurrency cap.

24Timed-Squares

A turn-based survival game on a 10×10 grid, recreated in HTML5 Canvas and vanilla JS. Originally built in Processing and Pygame.

The core rule

Strictly turn-based, not real-time. One key press moves the player one cell; the instant that resolves, every obstacle takes its own move; then it is the player's turn again. A move into a wall is a no-op — nothing advances, because nothing actually moved.

Telegraphing

Every obstacle shows what it is about to do before doing it, with an arrow rotated to the exact {dx, dy} it will execute. This is the design constraint, not decoration: the game is meant to be dodgeable by reading the board rather than memorising it, so the arrow must point at the real upcoming move. nextMove is decided once at spawn (so the first render already shows an arrow) and re-decided immediately after each execution — never both in the same step, which is what keeps "shown, then resolved next turn" true turn over turn.

ObstaclePattern
Standard1 cell/turn, straight line
Jumper2 cells/turn — can jump over an intervening cell, including the player, without colliding
L-moverKnight-style hop; always makes net progress along its spawn-edge axis, perpendicular sign chosen fresh each turn
Diagonal1 cell/turn diagonally, keeping the inward component from its spawn edge
BouncerReverses the instant its next step would leave the board — decided at telegraph time, so it never executes an exiting move

The leaderboard's deliberate asymmetry

sanitize_arcade_name allows digits ("P1AYER") and, on anything invalid, falls back to "ANON" rather than rejecting the submission. The reasoning: the score was already earned by actually playing, and a malformed name should not cost the player that — the way a malformed field should block a form before anything of value has happened.

No server-side replay validation. POST /api/scores only checks the submitted turn count is a plausible non-negative integer under a ceiling. A determined visitor could POST a fabricated score. Accepted as a documented simplification at this scope — the same "simulation only" spirit as the trading book having no real money, applied to a leaderboard number.

The layering, stated precisely

If asked "how do you prevent SQL injection"

The honest answer is parametrised queries — every query in the app uses SQLAlchemy bound parameters, including the raw SQL in analytics.py, which takes no user input at all. Claiming the whitelist is what stops injection would be the wrong answer even though the whitelist is real and does reject those characters.

Hashed profanity blocklist

A mechanism test is not an effectiveness test

That blocklist shipped to production seeded with three deliberately-mild placeholder words. A visitor named a character with real profanity, it passed Test: Profanity, and went live. The hashing, the stage wiring and the never-reach-the-world path all worked exactly as designed and tested — the data backing the check was a demo. No passing test could have caught that, because the tests only ever asserted the mechanism worked against whatever list was configured.

Remediation had two halves: replace the list, and fix the row that was already wrong — set status='failed', write a real PipelineRun recording why, invalidate the cache. Production data that is already wrong needs correcting directly, not just the code fixed for next time.

Other posture

  • No code execution surface. Pipeline World's entire input is a name, picks from fixed lists, and four text answers. There is no path that treats visitor input as anything but a string to validate and store — a stronger guarantee than "we sandboxed it".
  • Secrets. Production refuses to boot on the default SECRET_KEY. Real OAuth credentials found in the legacy repo were purged from git history with git-filter-repo and force-pushed after verifying by path and by grepping every blob for the client ID string — a rename would have defeated a path-only check.
  • Request size. MAX_CONTENT_LENGTH caps bodies at 1 MB.

Limits are proportional to what one call actually costs downstream, not uniform.

2. SSE concurrency caps

The scarce resource is the eight-slot gunicorn thread pool. Each SSE connection holds one thread for as long as the tab stays open, so without a cap a handful of connections could occupy every slot and hang the entire site, not just degrade one feature.

GLOBAL_SSE_CAP     = 4   # across all feeds, leaves 4 threads for page loads
CATEGORY_SSE_CAP   = 3   # one feed cannot eat the whole global budget
PER_CLIENT_SSE_CAP = 2   # one visitor cannot exhaust either of the above

All three are checked on every connection attempt. Counters are Redis INCR/DECR pairs released in the generator's finally block, so a normal disconnect always cleans up. As a safety net against a worker crashing and skipping that finally, each counter gets a TTL the first time it is created — deliberately not refreshed on later connections, or continued traffic would push the expiry out forever and a leaked count would never self-heal.

Redis rather than an in-process semaphore, because an in-memory counter would only cap this one process's share and would not hold if the app ever scaled to multiple replicas.

3. Per-session caps

Ten open strategies per session. Bounds how much one visitor can clutter a shared public book — a persistent limit, which a rolling rate-limit window cannot express.

27Failure handling patterns

Four recurring patterns, each with a specific reason.

Graceful degradation at every integration point

Both external clients wrap their network calls broadly and re-raise one clean domain exception — MarketDataError, EdgarError — so routes can render an "unavailable" state rather than a 500. The lesson that produced this: market_data.py already did it, edgar.py did not, and a requests timeout sailed straight past the route's except (MarketDataError, EdgarError) handler. A graceful-degradation pattern has to be applied at every integration point individually — copying it to one call site does not protect the others.

Catch-all at orchestration boundaries

_run_stage catches ValidationError for expected failures and a bare Exception for everything else, logging the real traceback while showing the visitor a generic message. Every stage must end in a real pass or fail; there is no third state.

Failures stay queryable

A failed RiskRequest is persisted with status='failed' and its reason, not deleted. A failed character keeps its PipelineRun history and failure_reason. A failed attempt is a fact worth keeping — the same way a real risk run failing does not erase that it was attempted.

Never leak internals to the visitor

Stage crashes surface as "internal error -- this stage did not complete". The traceback goes to current_app.logger.exception. Validation failures, by contrast, are shown verbatim because they are actionable and contain nothing internal.

Two tests worth describing on their own

Column widths — a guard against an invisible class of bug

Tests run on SQLite, which ignores VARCHAR length limits entirely. Postgres enforces them. So a too-narrow column is invisible to every other test and only appears as a 500 in production. It happened twice: PipelineRun.stage was String(10) while 'test_uniqueness' is 15 characters, breaking the pipeline mid-run; Instrument.instrument_type was String(4) while 'stock' is 5, breaking every stock position.

tests/test_models_column_widths.py checks the declared width of every string column against the widest value the code can put in it, reading from the actual constants and registries rather than copies. It touches no database, so it catches the problem under SQLite just as well as Postgres. It has since caught a bug it was not written for: adding Instrument.code at String(24) tripped it immediately, because the real worst case is 25 characters. A coverage-style guard beating a bug-specific one is the whole argument for writing it that way.

No PASS to the right of a FAIL

A test submits a submission that fails at stage 4 and asserts every stage after it is None in the tracker payload — encoding the invariant "a failed pipeline stops" as something the suite enforces, not just something the code happens to do.

Migrations

Alembic through Flask-Migrate. The recurring trap, hit four times: adding a nullable=False column to a populated table generates SQL that fails immediately, because Postgres backfills existing rows with NULL before checking the constraint. The fix is always the same shape — add nullable, backfill with a real value in the same migration, then tighten to NOT NULL. Two flavours of backfill: a single constant works via server_default; a value that varies per row (each instrument's own OCC code) needs an actual loop.

Walk me through this project.

Lead with structure, not a feature list. One Flask app, ten blueprints, six substantial projects sharing one Postgres, one Redis, one worker pool, deployed as five containers on a VPS. Routes are thin; logic lives in a service layer; models hold state.

Then pick one project and go deep rather than skimming all six. Pipeline World is the strongest choice because it exercises the most: a queue, a separate worker process, WebSocket push, cache-aside, and real SQL over the data it produces.

Close with the constraint that shaped the deployment: gunicorn runs a single process because Socket.IO sessions live in process memory, which makes the eight-thread pool a real budget and explains the SSE caps and the static-file split. §1 §2

What was the hardest part?

Good candidates, in rough order of how well they demonstrate systems thinking:

  • Moving risk pricing to a separate process. The interesting part is not "I added a queue" — it is that exceptions stop working as a communication channel across a process boundary, and the shared database row has to carry both the result and the failure. §10
  • Realising the upfront validation was the bug. A correct-looking guard was deleting the observability the project existed to demonstrate. §18
  • The static-asset bottleneck. A resource limit that was correct for its own reason was still a bug everywhere else that resource got used. §29

Architecture and design

Why a separate worker process instead of doing the work in the request?

Two different reasons for the two job types, and saying so shows you did not just apply a pattern uniformly:

  • Pipeline World is genuinely fire-and-forget. The request returns immediately, and progress reaches the browser over WebSockets. Stages take 1–10 s each by design; holding a thread for a minute would be indefensible.
  • Risk pricing is submitted and then awaited — the caller still gets a finished report back synchronously. The win there is that the compute happens off the web process, echoing how a desk distributes to a grid, while callers keep a simple synchronous contract.

Be ready for the follow-up: the wait polls the row's status every 50 ms with a 20 s ceiling, and must use a column query rather than session.get(), which would be served from the identity map and never re-read. §10

You have two risk models. Why, and how is that structured?

Strategy pattern with a registry. RiskModel defines run(ctx) -> ModelRun plus self-describing metadata; the request stores which key answered.

The models answer genuinely different questions: closed-form Greeks are local derivatives around today's spot and cannot tell you what a 20% gap does; full revalue reprices across a ladder and measures the P&L it observes. A desk runs both and treats a disagreement as a signal.

The key design point: the engine owns all side effects — market fetch, scenario shock, DB writes — and hands the model a frozen PricingContext. So two models see byte-identical inputs, and a model is testable with no network and no database. §11

Why one market snapshot per request instead of pricing each leg as you reach it?

This is the single best correctness answer in the project. Pricing legs one at a time marks a multi-leg position against several different instants, so the net Greeks describe a position that never existed at any one moment. A spread's two legs offsetting each other is only meaningful if both were marked against the same market.

So take_market_snapshot() fetches one price per distinct ticker up front, and the snapshot is stored in totals so the report can prove what it was marked against. §10

Why keyword-only arguments on submit_risk_request?

It previously took a leg id positionally. Adding a strategy_id parameter meant a stale submit_risk_request(42) would be silently reinterpreted as "price position 42" — a wrong answer with no error and nothing to notice.

The general principle: a signature change that silently changes an existing positional argument's meaning is exactly the case worth making unrepresentable. It turned into an immediate TypeError, and 11 stale call sites in the suite failed loudly instead of quietly pricing the wrong thing. §10

Why is Instrument separate from Leg?

Reference data versus transaction data. A hundred visitors trading the same AAPL $230 call should point at one instrument row, not each embed a private copy of the strike, expiry, exercise style and multiplier. That is how real booking systems separate the concerns, and it is what makes the instrument catalogue — "show me every leg across every position that has ever traded this contract" — a real query rather than a scan.

Enforced by a unique constraint on the natural key plus a single get_or_create_instrument() entry point. Passthrough properties on Leg meant the refactor did not touch the routes and templates. §7 §8

Why SSE in some places and WebSockets in others?

Use the simpler tool wherever it suffices. SSE is one-way server→client over plain HTTP, needs no client library and reconnects on its own — correct for the watchlist, which only ever pushes prices down.

Pipeline World uses Socket.IO because the spec asked for it and because a bidirectional protocol is defensible once client-originated events are plausible. Say plainly that the current version is push-only in practice. The answer to avoid is "WebSockets because they are more impressive". §13 §18

Databases and SQL

Walk me through the rolling 7-day pass rate query.

A CTE aggregates runs into one row per day using DATE_TRUNC('day', started_at) and COUNT(*) FILTER (WHERE status='pass')::float / COUNT(*) — the cast matters or integer division floors it to zero.

The outer query applies AVG(...) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW). Be ready to explain that the explicit frame is what makes it a trailing seven-row window; the default frame would give a running average over all prior rows.

Also be ready for ROWS vs RANGE: ROWS counts rows, so a day with no runs is skipped rather than counted as a gap — acceptable here, and worth naming as a known property. §20

Why does one page require Postgres when everything else runs on SQLite?

The page exists to demonstrate real SQL. DATE_TRUNC, FILTER and window frames are Postgres dialect; rewriting them in a portable subset would mean dropping the window functions or reimplementing them as Python loops, which would undercut the exact thing being shown.

The engineering answer is what surrounds it: every ORM model stays on portable types so the rest of the app works either way, the module checks the dialect and raises a clear message telling you how to point DATABASE_URL at Postgres, and the tests skip with a reason rather than silently passing on fake data. §20 §28

Tell me about a migration that went wrong.

Adding a nullable=False column to a populated table — hit four separate times. Alembic's autogenerated SQL fails immediately because Postgres backfills existing rows with NULL before checking the constraint.

The fix is always the same shape: add nullable, backfill in the same migration, then tighten. Distinguish the two backfill flavours: a single constant works via server_default; a value that varies per row — each instrument's own OCC code — needs a real loop, which server_default cannot express. §28

How do you prevent SQL injection?

Parametrised queries — SQLAlchemy bound parameters everywhere, including the raw SQL in the analytics module, which takes no user input at all.

Then the important qualifier: the input whitelists and the injection scan are defence-in-depth on top of that, not the mechanism. Claiming the whitelist is what stops injection would be the wrong answer even though it is real and does reject those characters. §25

You tested on SQLite and deployed on Postgres. What broke?

Column widths. SQLite ignores VARCHAR limits entirely; Postgres enforces them. So a too-narrow column is invisible to a green test suite and appears only as a production 500. It happened twice — PipelineRun.stage at String(10) against the 15-character 'test_uniqueness', and Instrument.instrument_type at String(4) against 'stock'.

The response is the good part: rather than fixing them one outage at a time, a test now audits every string column's declared width against the widest value the code can write, reading from the real constants. It touches no database, so it catches the class of bug under SQLite. It later caught a bug it was not written for. §28

Concurrency, caching, infrastructure

Explain your caching strategy.

Name the pattern — cache-aside — and then explain why both mechanisms are present. Reads try Redis, fall back to Postgres on a miss, repopulate. The cache is explicitly invalidated the moment a character clears Deploy.

TTL alone would mean a newly-live character might not appear for up to 30 s, which is fine for many caches and wrong here, where "does this feel live" is the product requirement. Explicit invalidation handles the common case; the TTL is the safety net if an invalidation is ever missed. Either alone is a weaker version of the pattern.

Separately, PriceCache is a plain read-through TTL cache in Postgres — different problem (third-party rate limits), different solution. §12 §19

How do you stop one visitor degrading the site for everyone?

Three mechanisms protecting different resources, and the distinction is the answer:

  • Rate limits bound request frequency per IP, sized to what each call costs downstream — 5/hour for a backtest that makes four API calls per ticker, 300/hour for a cached read.
  • SSE concurrency caps bound something a rate limit cannot express: a connection that holds a thread indefinitely. Global 4, per-category 3, per-client 2, against an eight-thread pool.
  • Per-session caps bound accumulated state — ten open positions — which a rolling window cannot.

Follow-up worth pre-empting: the counters are in Redis, not process memory, because an in-process semaphore only caps one process's share and would not survive scaling out. And the TTL is set only on first creation, or continued traffic would push the expiry out forever and a leaked count would never self-heal. §26

Why one gunicorn worker? That seems wrong.

Agree that it looks wrong, then give the reason. Flask-SocketIO's threading mode keeps each client's Engine.IO session in the memory of the process that created it. With multiple worker processes, consecutive polling requests for one session get round-robined to a process that has never seen it and return 400 unknown session — live updates break silently while the pipeline itself still completes, because that part only depends on Postgres and Redis.

So concurrency comes from eight threads instead, and the threads are then treated as a real budget: SSE caps sized against it, and static files moved off it entirely. The honest scaling answer is that a Redis message-queue backend for Socket.IO is what would allow multiple processes. §2 §26 §29

Your dev machine has no Redis. How do tests and local dev work?

Three environments, three behaviours: real Redis with a separate worker container in Docker; fakeredis with a worker thread locally; fakeredis with RQ synchronous in tests.

The point to make is about the middle one: the fallback preserves the property under test. Running the pipeline inline when Redis is absent would demo identically and lie about the architecture. A real worker in a background thread means the request still returns immediately and stages still progress over wall-clock time.

Two portability findings came out of it: RQ's default worker forks per job and os.fork() does not exist on Windows, so SimpleWorker is used everywhere — one tested path, not two, one of which would only run in production; and signal handlers only install on a main thread, needing a one-method override. §22

How does a failure travel from the worker back to the web process?

Through the database row, because an exception cannot cross a process boundary — there is no shared call stack to unwind and no in-memory future to await.

The worker catches its own exceptions and writes a plain-text reason onto RiskRequest.error. The waiting web process re-derives the same exception type from that string once the row stops reading pending, so every existing except MarketDataError handler keeps working without knowing pricing moved processes. The shared state carries both the result and the failure. §10

Quantitative and domain

Where do your Greeks come from?

Computed locally from Black-Scholes closed forms — yfinance exposes an option chain but no Greeks. Be able to write d1 and d2 and say the CDF is 0.5*(1+erf(x/sqrt(2))), no SciPy for one function.

The part that shows domain awareness is the quoting conventions: theta divided by 365 so it reads per calendar day, vega and rho divided by 100 so they read per one point. Raw annualised numbers are correct and useless to a trader.

Then the honest limitation, unprompted: implied vol is captured at entry and held constant, because there is no live vol surface available. A real desk reprices off a fresh surface. §9

You report gamma twice. Why?

They are different computations. Analytic gamma is the closed-form second derivative — the formula's curvature at a point. scenario_gamma is empirical: reprice at spot ±1% around the run's own base and measure how much the P&L actually curves, which is what "scenario gamma" means on a risk desk.

For a vanilla option with no exotic kinks they should agree closely, which makes the comparison a free self-check — a disagreement is a real signal that something is wrong. §11

What is IR Vega and how can you compute it under a flat rate?

You cannot — that is the honest opening. A constant rate has no volatility to be sensitive to, so IR Vega is structurally impossible under the model everything else uses.

So a minimal Hull-White one-factor short-rate extension is added only for this measure. Assuming zero correlation between rate and equity Brownian motions, the standard result is to price with ordinary Black-Scholes but replace the equity variance with an adjusted total variance that adds the rate process's contribution; that integral has a closed form. IR Vega is then a central finite difference on the rate-vol parameter.

State the limitation plainly: both parameters are assumed illustrative constants, not calibrated, because yfinance has no cap or swaption vol surface to calibrate against — the same situation the flat risk-free rate is already in. Every other number on the row still uses the flat-rate maths. §9

How does your backtest avoid look-ahead bias?

By filtering SEC facts on filing date, not period-end date. A fiscal year ending in December is not filed until February or March; scoring "as of a year ago" with period-end data would hand the model information nobody had at the time, and any correlation found would be an artefact of that leak.

Be honest about scope: a handful of tickers and one lookback window is demo-scale validation, not research-grade. Naming that limitation is stronger than overselling it. §14 §16

A company is missing a metric. What does your score do?

Drops the metric and renormalises the remaining weights over what is actually available. Walk through why the alternatives are worse: erroring out makes the tool useless against real filings, and treating missing as zero is actively wrong — it scores the company as terrible at something that was simply not measured.

The response returns both weights_configured and weights_used, so the page can show the composite was computed over three categories rather than four. Weights are config, overridable per category by environment variable, not hardcoded. §15

Debugging and judgement

Tell me about a bug that only appeared in production.

The strongest one: a pipeline stage crashed for a reason unrelated to validation — most likely the worker container being killed mid-job by a redeploy. _run_stage only caught ValidationError, so nothing handled it: no run row, no fail event. Because Verify runs after Deploy already committed status='live', a character was left live with a blank gap in its own history — not failed, not passed, missing, which the UI could not render as an error because nothing had raised one it was watching for.

Found from a screenshot of a blank cell, not a log. Fixed with a catch-all at the orchestration boundary, and the already-broken row was corrected directly in production. The lesson: a try/except scoped to the errors you expect is a statement about the happy path, not a safety net. §17 §27

Tell me about a time your tests passed but the code was wrong.

The profanity filter. The hashed blocklist mechanism worked exactly as designed and tested — but it shipped seeded with three placeholder words, so real profanity passed the stage and went live. No test could have caught it, because the tests only ever asserted the mechanism worked against whatever list was configured.

The generalisable point: a mechanism test is not an effectiveness test. "Defence-in-depth" and "tested" mean little if the data behind the check was never filled in. Remediation had two halves — fix the list, and fix the row that was already wrong, since production data that is already incorrect needs correcting directly rather than just the code fixed for next time. §25

Describe a time you removed a check rather than adding one.

Pipeline World validated at the join route: charset, injection and profanity ran upfront so bad submissions never became jobs. Sensible-looking, and it broke the product — a visitor who typed a blocked word got a red message and no pipeline run at all, so the most interesting thing the system does was the one thing nobody could watch.

Every check moved into the stage that owns it; the route now only strips and truncates. This also required raising the storage caps above the validated limits, or an over-long entry would be truncated into a passing value and the stage would approve something never submitted.

The point: "fail fast" and "fail visibly" are different goals, and validating early can delete the observability that was the reason for building the thing. §18 §25

Tell me about a debugging session where the obvious cause was wrong.

Two good ones:

  • NaN in JSON. An option chain failed in the browser but looked perfect through curl | python -m json.tool — because Python's json accepts a bare NaN as a non-standard extension and the browser's JSON.parse correctly does not. Two tools disagreeing about what "valid JSON" means. The regression test uses a strict parser, plus a second test proving that parser would reject NaN — otherwise the guard could quietly stop testing anything.
  • Characters not talking. Reported as a broken conversation feature. The seek logic, notice radius and trigger distance were all correct; the map was a grid of buildings, and direct steering with wall-bounce cannot route around an obstacle, so two characters who had noticed each other bounced against the wall between them forever. The fix was an open field, not a smarter algorithm. An agent-interaction bug that was really environment design.

How did you handle finding secrets in the repository?

In stages, each matched to its blast radius. First remove from the working tree with an ordinary commit — non-destructive and safe immediately. Then, when clearing history was authorised, clone into an isolated directory and run git-filter-repo.

Two details that show rigour: diffing which paths had ever existed found a second, older exposure at a path that predated a reorganisation; and verification grepped every blob in history for the actual client ID string, not just paths, because a rename would defeat a path-only check. Force-push only after that passed.

Close with the part people forget: rewriting history does not rotate the secret. It stops future clones finding it; it does not invalidate anything that already saw it. Rotation is still required. §25

Trade-offs and self-critique

What would you do differently, or what does not scale?

Have several ready and be specific:

  • Single gunicorn process. The Socket.IO constraint that forces it is solvable with a Redis message-queue backend; until then horizontal scaling is blocked.
  • Traffic buffer is in-memory and per-process. Fine for a rollup, wrong for an audit trail, and it would fragment across replicas.
  • Synchronous wait on risk requests. Simple contract, but it still ties up a request thread. A job-id-plus-poll or push-on-complete API would free it.
  • Entry IV held constant. The right fix is a vol surface, which needs a paid data source.
  • No replay validation on game scores. Deliberate at this scope and openly documented.
  • Scoring bounds are broad heuristics, not sector-tuned — a P/E of 12 means different things for a bank and a software company.

Naming these unprompted reads as judgement. Waiting to be caught on them does not.

Is the pipeline's "test stage" actually running tests?

Answer directly: no, it does not shell out to pytest. It calls the same validator functions that tests/test_validators.py covers.

The reasoning: invoking pytest.main() per character inside a worker loop is slow, fragile, and awkward to feed per-character data into, since test functions are designed for pytest's collection mechanism. The choice is genuinely tested code running live rather than a parallel fake implementation.

It is a documented trade-off, not a free lunch — and saying that is much stronger than overclaiming "it is literally pytest under the hood". §17

Why does the traffic project only log your own traffic?

Because capturing arbitrary visitors' browsing is treated as wiretapping in most jurisdictions regardless of intent, and would violate essentially any host's terms of service. The scope was set by that constraint first, then built to it: inbound requests to the app's own routes, and outbound calls the app itself makes.

This is a "how do you think about constraints" question more than a technical one. The good version shows the limit was designed around deliberately, not discovered late. §23
